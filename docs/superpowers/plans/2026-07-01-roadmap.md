# nerd-butthurt-alert — Implementation Roadmap

> **For agentic workers:** This is the milestone map, not an executable plan.
> Each milestone gets its own detailed plan under
> `docs/superpowers/plans/`, written with full bite-sized tasks when its turn
> comes. Execute milestones in order with
> superpowers:subagent-driven-development. Detailed plans for M2–M5 are
> written **after** the milestone before them lands and pins real interfaces
> — writing complete code for them now would be speculative churn.

**Source of truth:** the v0 specs in `docs/specs/` (ARCHITECTURE,
OBSERVABILITY, PROBE_PAYLOAD, STORAGE_SCHEMA, SIGNAL_RULES, CONFIG_FILE,
PATH_DEPLOYMENTS, TOOLING). The specs are the design; these plans only
sequence and operationalise them.

**Ordering principle — vertical slice first.** Milestone 1 builds the
thinnest end-to-end path that runs and is observable: one target, one
(direct) path, `http_get` → SQLite → `/metrics` → a Prometheus scrape you
can watch. Get a _running_ system early, then layer breadth (more check
types, proxied paths, signals, Grafana) onto a spine that already works.
This ordering is deliberate and load-bearing: it is the hedge against the
project's standing failure mode — chasing an unbounded surface (full probe
fidelity, the rule catalogue, exhaustive test coverage) before anything
runs. Hold it.

## Milestone sequence

### M1 — Vertical slice ✅ _(detailed plan: `2026-07-01-milestone-1-vertical-slice.md`)_

**Goal:** a running service that probes one target over the direct path with
`http_get`, persists each probe to SQLite, exposes `/metrics`, and is scraped
by a local Prometheus you can open in a browser.

**In scope:**

- Project scaffold + full toolchain (pnpm, TS strict, ESLint, Prettier,
  Vitest, markdownlint, EditorConfig, native git hooks, commitlint).
- Config loader: layered TOML (`default` → `<NODE_ENV>` → `local`) + Zod
  validation, for the `[metrics] [storage] [scheduler] [probes] [[paths]]
[[targets]]` sections. (Rule config passed through, not yet consumed.)
- Storage: `node:sqlite` open + pragmas (WAL load-bearing), migration
  runner, `probes` table + its three indexes, probe insert,
  `first_failure_code` derivation, latest-per-cell reader.
- Probe engine: `http_get` via Playwright (Chromium), **direct path only**,
  built on Playwright's high-level API (navigation, response, body,
  security details, timing); the `net::ERR_*` → failure-code mapping.
- Scheduler: `croner` with no-overlap protection.
- Metrics exporter: `prom-client` + `node:http`, the probe gauges +
  counters + `nba_build_info`, seeded at startup and updated in-process.
- Provisioning: `prometheus.yml` + a minimal `docker-compose.yml` running
  Prometheus against the host service.

**Deferred to later milestones (named so M1 stays minimal):**

- SOCKS5 / proxied paths, `dns_lookup`, `tcp_connect` → **M2**
- CDP-native per-hop fidelity (full cert chain via `getCertificate`, per-hop
  dns/tcp blocks, `network_events`, `all_headers` overflow, body-stall
  byte-counting, subresources, impersonation→engine, restricted ports) → **M2**
- `signals` table, rule engine, the 17 rules, signal metrics → **M3/M4**
- Grafana datasources + dashboards + full containerized compose → **M5**
- Retention cleanup job, full annotated `default.toml` for rules → **M2/M4**

**Demo:** `pnpm start` + `docker compose up`, then a Prometheus graph of
`nba_probe_up` / `nba_probe_latency_ms` for the configured target.

**Build vehicle:** SDD, task by task.

### M2 — Probe engine completion

**Goal:** full `PROBE_PAYLOAD.md` fidelity across all three check types and
all path types.

**In scope:**

- A minimal SOCKS5 client (CONNECT, no-auth) — the shared seam for proxied
  `http_get` (Playwright `proxy`), `tcp_connect`, and `dns_lookup` tunnelling.
- `dns_lookup` (system / udp53 / dot / doh; DoT/DoH-over-CONNECT default for
  non-direct paths) and `tcp_connect` (`node:net` direct, SOCKS5 CONNECT
  proxied). `attempt_all_ips`.
- CDP-native `http_get`: per-context-per-path browser reuse, per-hop dns/tcp
  blocks, full peer-cert DER chain via `Network.getCertificate`,
  `negotiated_protocol`/ALPN, `all_headers` overflow, `network_events`,
  body-stall detection by inter-byte idle timeout, `subresources`
  (first-party eTLD+1 health), restricted-port (`ERR_UNSAFE_PORT`) handling,
  impersonation profile → browser engine (Chromium/Firefox/WebKit).
- Full `first_failure_code` derivation walking real sub-op `failure` fields.
- Retention cleanup job (daily delete of probes older than `retention_days`).

**Depends on:** M1 storage + probe seams.

**Build vehicle:** SDD; the check-type implementations can fan out once the
SOCKS5 seam exists.

---

### M3 — Signals engine core

**Goal:** the rule runtime — discover rules, run them on the right trigger,
persist signals through the lifecycle, expose signal metrics.

**In scope:**

- `signals` table + migration (active/cleared, unique-active index).
- `Rule` contract + `RuleInput`/`RuleOutput`/`ProbeRecord` types
  (`SIGNAL_RULES.md`).
- `StorageReader` (`recentProbes`, `latestPerCell`, `payload`).
- Auto-discovery of `src/signals/rules/*.ts`; per-rule config merge
  (`defaults` ← `[rules.<name>]`); `enabled` gate; error isolation
  (a thrown rule is logged, never crashes the layer).
- Evaluation triggers: single-probe / target-window on each insertion;
  cross-path at the per-target **sweep barrier**.
- Lifecycle writer (fire-new / fire-continuing / clear) and signal metrics
  (`nba_signal_active`, `nba_signal_confidence`), seeded + in-process.
- 1–2 reference rules to prove the contract end-to-end.

**Depends on:** M1 (storage, exporter, scheduler), M2 (real payloads to
evaluate).

**Build vehicle:** SDD.

---

### M4 — The 17-rule catalogue

**Goal:** implement the full `SIGNAL_RULES.md` catalogue.

**In scope:** all 17 rules, each a single file under `src/signals/rules/`,
each TDD'd against the contract with fixture probes, each with its
`defaults` block written into `default.toml`.

**Depends on:** M3 (the contract + harness must be frozen first).

**Build vehicle:** **ultracode Workflow** — the rules are the project's one
embarrassingly-parallel chunk (uniform contract, independent files). Fan out
one implementer per rule against the frozen contract + a shared fixture set,
then an adversarial verification pass per rule (does the predicate match the
spec's fires/clears wording? does it short-circuit on the wrong check type?
does it return `clear` only when affirmatively false?).

---

### M5 — Grafana + full provisioning

**Goal:** zero-click observability stack.

**In scope:**

- Grafana datasources (Prometheus + `frser-sqlite-datasource`, read-only WAL).
- The five dashboards as committed JSON (status matrix, latency-over-time,
  signal activity, probe drill-in, freshness) + `reached_stage` value
  mappings + dashboard providers.
- Full `docker-compose.yml`: the Node service (with a Dockerfile),
  Prometheus, and Grafana, with `probes.db` bind-mounted read-write into the
  service and read-only into Grafana.

**Depends on:** M1 (`/metrics`), M2 (real evidence to drill into), M4
(signal metrics to chart). Dashboards referencing signals need M4 data.

**Build vehicle:** mostly static config — written directly, light SDD.
Dashboard JSON is the only fiddly part.

## Cross-cutting, folded where they land

- **`CLAUDE.md`** (durable agent-facing conventions: push policy, commit
  policy, structure) — write alongside M1 once the scaffold exists, so every
  later agent inherits it. (`TOOLING.md` is its source.)
- **`default.toml`** grows per milestone — M1 ships metrics/storage/
  scheduler/probes/shape_detection; M4 appends every rule's defaults.
- **Verification passes at milestone boundaries** — a spec↔implementation
  conformance audit and an adversarial code-review of the diff before each
  merge (the machinery that worked on the docs coherence review).
