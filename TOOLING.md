# Tooling and Conventions (v0)

## What this document is

A companion to the other sub-documents. It covers the **developer-
side toolchain** — formatters, linters, type checkers, test runner,
package manager, Git hooks, commit conventions, push policy —
distinct from `ARCHITECTURE.md`, which covers the runtime stack.

The pitch: declare every tool and convention up-front so future
work (by the user or any agent) inherits a consistent
environment without per-file rediscovery.

## EditorConfig

A committed `.editorconfig` at the repo root locks the basics
across editors:

```ini
root = true

[*]
charset = utf-8
end_of_line = lf
indent_style = tab
indent_size = 4              # display width for tabs in editors
insert_final_newline = true
trim_trailing_whitespace = true

[*.md]
trim_trailing_whitespace = false   # preserve double-space line breaks
```

Prettier respects EditorConfig settings (`useTabs`, `tabWidth`,
`endOfLine`), so tab character and width propagate automatically
without restating in `.prettierrc`.

## Package manager: pnpm

`pnpm` over npm/yarn/bun because:

- Stricter dependency graph — no phantom-dep imports of transitive
  packages.
- Content-addressable store — smaller disk footprint, faster
  installs once warm.
- Mature workspace support, should we ever need it.

Pin in `package.json`:

```json
{
  "packageManager": "pnpm@<latest>",
  "engines": {
    "node": ">=26.0.0"
  }
}
```

The `packageManager` field enforces the chosen manager via Corepack;
contributors using a different one get a clear error.

## TypeScript

Latest stable. `tsconfig.json` (extends the SvelteKit defaults
generated by `.svelte-kit/tsconfig.json`):

```jsonc
{
  "extends": "./.svelte-kit/tsconfig.json",
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "verbatimModuleSyntax": true,
    "noImplicitOverride": true,
    "noFallthroughCasesInSwitch": true
  }
}
```

`strict` + `noUncheckedIndexedAccess` together are the meaningful
upgrade over a casual setup; they catch the bulk of common bugs.

## ESLint

ESLint 10+ flat config (`eslint.config.js`). Required plugins:

- **`typescript-eslint`** (v8+) for TS rules
- **`eslint-plugin-svelte`** for `.svelte` files

ESLint's job is **lint** (correctness, smells, bug patterns), not
**format**. Formatting is Prettier's job; stylistic rules in ESLint
(quotes, spacing, etc.) are explicitly disabled where they'd
overlap.

Flat config sketch:

```js
import js from "@eslint/js";
import ts from "typescript-eslint";
import svelte from "eslint-plugin-svelte";

export default [
  js.configs.recommended,
  ...ts.configs.strict,
  ...svelte.configs["flat/recommended"],
  {
    rules: {
      // project-specific rules
    },
  },
];
```

## Prettier

Prettier (latest) with `prettier-plugin-svelte`. Tab character and
width come from `.editorconfig` — no need to repeat.

`.prettierrc`:

```jsonc
{
  "plugins": ["prettier-plugin-svelte"],
  "overrides": [
    { "files": "*.svelte", "options": { "parser": "svelte" } }
  ]
}
```

No more config than needed; Prettier's defaults are the point.

## Stylelint

`stylelint` for CSS — both `.css` files and `<style>` blocks in
`.svelte` files. Standard config plus the Svelte parser:

```js
export default {
  extends: ["stylelint-config-standard"],
  overrides: [
    {
      files: ["**/*.svelte"],
      customSyntax: "postcss-html",
    },
  ],
};
```

## Markuplint

HTML linting for the markup inside `.svelte` components. Covers
accessibility hints, deprecated attributes, structural rules ESLint
doesn't see.

Some overlap with `eslint-plugin-svelte`'s a11y rules. The overlap
is fine; Markuplint catches things ESLint doesn't (and vice
versa). Run both.

## markdownlint-cli2

Markdown linting for `*.md` files (spec docs in this repo are
non-trivial). Project config (`.markdownlint-cli2.jsonc`):

```jsonc
{
  "config": {
    "default": true,
    "MD013": false         // line-length: disabled (let editor wrap)
  },
  "globs": ["**/*.md"],
  "ignores": ["node_modules", ".svelte-kit"]
}
```

## svelte-check

`svelte-check` runs the Svelte language server's diagnostics over
the whole project — catches template-level type errors that plain
`tsc --noEmit` cannot see (e.g., wrong prop types on `<Component
foo={…}/>`).

Run in:

- The pre-commit hook (against the whole project — `svelte-check`
  is fast enough that partial runs aren't worth the complexity).
- Locally in the dev loop via `pnpm svelte-check --watch`.

## Vitest

Vitest as the test runner. Picked over Node's built-in `node --test`
because:

- Vite-native — uses the same transform pipeline as the dev server,
  so test imports work identically to runtime imports (no separate
  resolution config).
- SvelteKit testing docs and examples assume Vitest.
- DX gains (UI mode, watch mode, snapshots) that `node --test`
  doesn't match yet.

Layout convention: tests colocated next to source as `*.test.ts`.
Coverage via `@vitest/coverage-v8`.

## Browser support & Baseline

The project targets **`baseline newly available`** — the set of web
features interoperable across all core browser engines *today*
(supported everywhere, for less than the 30 months that would make
them "widely available").

### Why a Baseline tier, not a browser list

This is a single-user personal tool; the primary user runs Firefox
(desktop and Android) and keeps only Chrome around for testing. The
naive move would be to target Firefox specifically — but locking to
one engine is poor practice and ages badly. A **Baseline tier** is
engine-agnostic, principled, and tooling-enforced: it makes Firefox
(and every other current engine) a first-class citizen automatically,
without naming any of them. You target a *capability tier*, not a
browser.

`newly` rather than `widely` because it admits the modern primitives
this project leans on — CSS anchor positioning (Baseline 2026, shipped
Firefox 147), the Popover API, `<dialog>` — while still excluding
anything not yet interoperable. The actual MVP surface (`<dialog>`,
`<details>`, native `<select>`) is mostly *widely* available anyway,
so the tier carries comfortable margin; `newly` is headroom, not a
dependency.

What `newly` deliberately excludes — and what the linters below will
flag — is the Chromium-only sugar: `interestfor` (interest invokers),
anchored container queries (`container-type: anchored`), and
`appearance: base-select`. These must not be built on; redesign
around them rather than polyfilling (consistent with the
no-polyfill-graveyard stance — see the dashboard's tooltip note).

### The single source of truth

`browserslist` in `package.json`:

```json
{
  "browserslist": ["baseline newly available"]
}
```

`browserslist` v4.24+ resolves Baseline queries natively (no custom
tooling). The bundler (Vite) and the JS compat linter both read this
one config. For reproducible builds, pin a date or year later
(`baseline newly available on YYYY-MM-DD`, or `baseline 2026`); not
needed during active development.

### Enforcement

- **CSS — `stylelint-plugin-use-baseline`**, the official Stylelint
  plugin, backed by the `web-features` dataset (checks each feature's
  actual Baseline status, not inferred from resolved versions):

  ```js
  // stylelint config
  {
    plugins: ["stylelint-plugin-use-baseline"],
    rules: { "plugin/use-baseline": [true, { available: "newly" }] },
  }
  ```

  (`@supports` wrapping is the escape hatch for a deliberately
  out-of-tier feature.)

- **JS Web APIs — `eslint-plugin-compat`**, driven by the same
  browserslist target. Catches use of a Web API outside the tier
  (e.g. a too-new DOM method). Feature-detected usage
  (`if (foo) {...}`) is not flagged by default.

### Known gaps (accepted)

- **HTML / Svelte-template Baseline is not linted.** `@html-eslint`
  has a `use-baseline` rule, but this project uses Markuplint, and
  Svelte templates aren't plain HTML. The template-level exposure
  (a too-new HTML *attribute*) is tiny; not worth adding a second
  HTML linter. Accepted gap.
- **Vite build target.** Vite 7 defaults to `baseline widely
  available`; align it to `newly` at implementation (exact knob TBD
  during build setup).

## Commit conventions

Strict **Conventional Commits**, enforced via `commitlint` in the
`commit-msg` Git hook. Plain rules:

- **Subject format:** `type(scope): description`
- **Allowed types** (subset of CC spec):
  `feat`, `fix`, `refactor`, `docs`, `test`, `perf`, `chore`,
  `build`
- **Allowed scopes** (project-specific, extensible):
  `probe`, `signals`, `dashboard`, `api`, `storage`, `config`,
  `path`, `tooling`, `docs`, `deps`
- **Subject length:** ≤ 72 chars, no trailing period.
- **Body:** optional and **terse**. Required only when the *why*
  is non-obvious from the diff or subject. Bodies that just
  re-state the diff are noise; omit them.
- **No `Co-Authored-By:` trailers.** Whether the commit was
  authored by hand or with agent assistance, the trailer is not
  used in this project.
- **No `Signed-off-by:` either** (we don't run a DCO process).

`commitlint.config.js` — overrides on top of `config-conventional`
(everything else inherits from the upstream config):

```js
export default {
  extends: ["@commitlint/config-conventional"],
  rules: {
    // Narrow the upstream type list (drops "ci", "revert", "style").
    "type-enum": [2, "always", [
      "feat", "fix", "refactor", "docs", "test", "perf", "chore", "build",
    ]],
    // config-conventional has no scope-enum; we add one.
    "scope-enum": [2, "always", [
      "probe", "signals", "dashboard", "api", "storage", "config",
      "path", "tooling", "docs", "deps",
    ]],
    // config-conventional makes scope optional; we require it.
    "scope-empty": [2, "never"],
    // config-conventional defaults to 100; we cut to 72.
    "subject-max-length": [2, "always", 72],
  },
};
```

## Git hooks

Git's native hooks via `core.hooksPath`, **not** lefthook or husky.
For a single-developer project with our scope, the third-party
tools add a dep without buying anything we need.

### Bootstrap

A single `prepare` script in `package.json` configures the hooks
directory on first install:

```json
{
  "scripts": {
    "prepare": "git config core.hooksPath .githooks && chmod -R +x .githooks"
  }
}
```

`pnpm install` runs `prepare` automatically. A fresh clone is
ready to commit after one install.

### `.githooks/pre-commit`

Runs Prettier (check), ESLint, markdownlint on staged files only;
runs svelte-check across the project (it's fast enough that
per-file filtering isn't worth the complexity).

```bash
#!/usr/bin/env bash
set -euo pipefail

staged=$(git diff --cached --name-only --diff-filter=ACMR)
[[ -z "$staged" ]] && exit 0

code=$(echo "$staged" | grep -E '\.(ts|js|svelte)$' || true)
md=$(echo "$staged"   | grep -E '\.md$'             || true)
css=$(echo "$staged"  | grep -E '\.(css|svelte)$'   || true)

if [[ -n "$code" ]]; then
  echo "$code" | xargs pnpm prettier --check
  echo "$code" | xargs pnpm eslint --max-warnings 0
fi

if [[ -n "$md" ]]; then
  echo "$md" | xargs pnpm markdownlint-cli2
fi

if [[ -n "$css" ]]; then
  echo "$css" | xargs pnpm stylelint
fi

pnpm svelte-check --threshold error
```

### `.githooks/commit-msg`

Rejects `Co-Authored-By:` trailers, then runs `commitlint`:

```bash
#!/usr/bin/env bash
set -euo pipefail

if grep -iq '^Co-Authored-By:' "$1"; then
  echo "Co-Authored-By: trailer is not permitted in this project." >&2
  exit 1
fi

pnpm commitlint --edit "$1"
```

Both files committed to the repo, executable bit set by the
`prepare` script's `chmod -R +x .githooks`.

## Push policy

**Agents never autopush.** Any `git push` (or `git push --force`,
or any push variant) requires explicit human approval at the
prompt before execution. Enforced via `.claude/settings.json`
permissions — push commands are not in any auto-allow list and
trip the user-approval prompt by default.

This document records the policy; the enforcement lives in
settings.

## What's intentionally out of scope (v0)

- **CI / GitHub Actions / GitLab CI.** Pre-commit hooks are
  enough for a single-developer personal project. Re-evaluate if
  the project grows to multi-contributor or the user starts
  pushing from machines that haven't run `pnpm install`.
- **Renovate / Dependabot.** Default-noisy for a personal
  project. Manual `pnpm outdated` review when the user feels like
  it.
- **Spellcheck (`typos`, `cspell`).** Not worth the friction at
  this size.
- **`CLAUDE.md`.** Deferred until all substance specs are done —
  it'll consolidate the durable conventions for future agents
  (this push policy, the commit policy, the project structure,
  etc.) in one place. Currently `DASHBOARD.md` is the only
  pending substance doc; CLAUDE.md follows.
